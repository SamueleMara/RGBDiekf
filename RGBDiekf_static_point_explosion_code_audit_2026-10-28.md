# RGBDiekf — static-point explosion: source-grounded audit and covariance calibration

**Source:** `SamueleMara/RGBDiekf`, `main` commit `29a23a722aa98de137453717038054217a9ee5cb` (28 October 2026). This document does not modify code or claim a new rerun. It consolidates the empirical analysis of complete synthetic debug exports and the code audit. The newly supplied standalone HTML viewer templates contain no scene trajectories; their companion `debug/data/*.js` are required for real-case measurements.

## Evidence and limits

- Runaway positions occur in all six previously analyzed free forward/backward full-debug exports (USB, stapler, storage). Displayed-point maxima were approximately 17–51 m. Runaway points show initial large **accepted** corrections, a large acquired velocity, mask/FOV loss and long prediction-only stretches.
- Storage forward point `171031`: first-frame accepted position displacement ~0.2307 m, subsequent speed ~13.36 m/s; next frame has zero accepted cameras and the final displacement is ~13.36 m. The velocity direction is almost parallel to the position correction.
- USB forward point `81029`: ~0.576 m frame-2 correction, velocity ~20.06 m/s and no subsequent accepted observations; final displacement ~20.06 m.
- These facts establish the **state-update and ballistic-propagation chain**, not the identity of the exact individual camera measurement that caused the original false correction. Full `trace_frame_0001.json` / `trace_frame_0002.json` with rows and iterates is needed for that attribution.
- The new HTML attachments are **templates**, not independent measured evidence from new real runs. Their JavaScript references data files absent from the supplied HTML-only set.

## Direct failure mechanism

For an endpoint point, the free filter state is `s=[x,v]` with 6x6 covariance. Even though RGB-D observation Jacobians have zero direct velocity columns, the Kalman gain has a velocity block `K_v = P^-_{vx} H_x^T (H_x P^-_{xx} H_x^T + R)^-1`. Hence an accepted wrong 3D position correction creates an erroneous velocity. With no subsequent valid measurements, `x_{k+1}=x_k+dt*v_k`, `v_{k+1}=v_k`; no mean reversion exists or is implied by increasing covariance.

## Exact code positions, priority and evidence

1. **[P0, verified acceptance defect]** `estimator/point_kalman_cuda.py:246–253`: `observed = final['nrows'] > 0; s_plus = torch.where(observed[:,None], sj, s_minus)`; `converged` is not required. A nonconvergent iterate can be accepted and its covariance reduced as if the final local linearization were credible. **Do not simply reject every nonconverged update**: earlier ablation reduced static drift but also destroyed moving-part tracking. Instead analyze last statistically consistent iterate / measurement support and test recovery of legitimate dynamic motion.
2. **[P0, verified missing safeguard]** `estimator/point_kalman_cuda.py:218–245`: forms the local information system and blindly accepts the entire `delta`, with `sj += delta` at line 239. `step=delta^T A delta` (line 230) tests stopping, not acceptance of a nonlinear step or physical measurement validity. Large jumps can cross many pixels/surfaces; an exact local Jacobian does not guarantee global consistency. Add validation grounded in the actual projected RGB-D measurement model rather than a rendered-image optimizer.
3. **[P0, verified missing use]** `estimator/point_kalman_cuda.py:231–233,256–259`, `estimator/free_projective_run.py:182–183`: computes per-point prior normalized innovation squared (NIS) but only logs it. The gate in `projective_terms` is not a complete innovation-consistency check. Any statistical admission policy needs correct `P^-`, `R`, degrees of freedom and correlations; it cannot simply suppress legitimate rapid motion.
4. **[P0, verified modeling weakness]** `estimator/projective_terms.py:58–61`: rejects only the external-occlusion-explainable positive depth innovation `Z-D > n_sigma sqrt(S_zz)`; negative innovations are left as potential motion. Unit test `tests/test_projective_measurement.py:102–114` deliberately admits a point 1 m in front of the actual surface. A very large negative innovation is not automatically credible same-surface motion. Some large positive innovations can also survive if `S_zz` is large. This is **not a proof** that the asymmetric gate alone generated each runaway.
5. **[P1, fundamental observation ambiguity]** `estimator/projective_sensor.py:86–126`, especially `98–111`: locally valid 2x2 foreground and depth continuity cannot guarantee that a transported canonical point sees the same physical surface. The current policy `configs/projective_rgbd.json:4–8` permits a wide incidence angle (80 degrees) and 3-sigma depth consistency. For depth 1 m, focal 600 px, and assumed 1 cm depth sigma, the 2x2 permitted depth spread is about 5.6 cm. Even an absolutely flat wrong surface passes this test. Distinguish actual visibility/surface identity from interpolant validity without introducing temporal point matching.
6. **[P1, verified model approximation]** `estimator/projective_visibility.py:67–76`, `estimator/point_kalman_cuda.py:157–163`, `train.py:79–80`: default `per-frame` frozen pixel ownership is set at the predicted state. Later admitted points can project into pixels owned by others; suppressed points remain suppressed. This can make the measurement set inconsistent with the current iterate. Per-frame freezing reportedly helped a prior fixture but is not a correctness guarantee.
7. **[P1, conditional numeric defect]** `estimator/projective_sensor.py:98–125` computes interpolates and gradients on *invalid* raw neighbors, including possible NaN; `estimator/point_kalman_cuda.py:180–189` multiplies their `r`/`Hx` by weights zeroed via `where(valid,1/var,0)`. IEEE `0*NaN=NaN`: invalid rows can poison `Ixx`, `gx` and diagnostics; the analogous pattern exists in the rigid filter. Test with explicit NaNs, mask edges, nonfinite depths; select valid rows before algebra or ensure invalid term values are safe. This defect is **not demonstrated as the cause** of finite 13–50 m explosions.
8. **[P0, uncalibrated prior]** `configs/example_uncalibrated.json:186–234`, `scene/config.py:42–56`, `estimator/free_projective_run.py:74–79`: each point begins with zero mean velocity but `P_vv = I_3 (m/s)^2`, corresponding to 1 m/s componentwise standard deviation. This permits a large initial position/velocity coupling and lets a bad position update produce a spectacular velocity. This is not itself a mathematical code bug: it is a declared illustrative prior requiring calibration to the actual acquisition's physically plausible speeds.
9. **[P1, uncalibrated dynamics]** `configs/example_uncalibrated.json:97–129`, `scene/config.py:49–57`, `estimator/point_kalman_cuda.py:38–53`: continuous white acceleration density `q_c` is 0.01 m²/s³ on each translation axis. The signed-`dt` transition and integrated process covariance are algebraically appropriate for the model. The physical `q_c` must reflect acceleration changes, not static/dynamic labels. Decreasing `q_c` alone cannot damp the velocity **mean** once measurements disappear.
10. **[P1, uncalibrated measurement covariance]** `configs/example_uncalibrated.json:300–325`, `configs/projective_rgbd.json:9–13`, `estimator/projective_sensor.py:29–48,117–125`: RGB variance 0.0025 (sigma=0.05 in [0,1] units), depth variance 0.0001 m² (sigma=1 cm), with zero additive RGB/depth model-mismatch variance. Fixed source RGB across changing illumination/viewpoint, bilinear interpolation, calibration uncertainty and correlated pixels may violate these assumptions. Calibration must use real measurements, not artificially inflate R merely to suppress movement.
11. **[P1, statistical consistency]** `estimator/point_kalman_cuda.py:247–253`: the final inverse-information covariance is locally Joseph-equivalent under the assumed valid Gaussian linearization, but not a guarantee of correct uncertainty after invalid nonlinear measurement association or rejected convergence. `estimator/projective_terms.py:59–61` uses that prior covariance to determine which positive-depth residuals are considered externally occluded; inflated uncertainty can make the gate more permissive.
12. **[P2, diagnostics/coverage]** `estimator/free_projective_run.py:62–64,107–116`, `train.py:88–92`: default traces only six source point IDs at selected frames. For exact root cause, trace known runaway IDs and first bad frames and save per-camera admitted residuals, `S_zz`, Jacobian, `P^-`, gain, posterior, local convergence and reason codes.
13. **[P2, not an error]** `estimator/point_kalman_cuda.py:38–53,251–253`: a prediction-only state retains its velocity mean under a constant-velocity model. This explains escape after measurement loss but is **not** a signed-time or covariance-propagation bug. Adding artificial static attraction would violate free motion and harm tracked moving parts.

## Quantitative physical calibration

Current effective defaults:

| Parameter | Code origin | Value | Physical consequence |
|---|---|---|---|
| `P_vv,0` | `configs/example_uncalibrated.json:186–234` via `scene/config.py:50` | diag(1,1,1) m²/s² | Initial per-axis velocity sigma 1 m/s; isotropic 99%-probability speed sphere radius ~3.37 m/s |
| `q_c` | `configs/example_uncalibrated.json:97–129` via `scene/config.py:50` | diag(.01,.01,.01) m²/s³ | At dt=1/59s, process-induced per-axis velocity sigma increment ~0.013 m/s |
| `R_depth` | `configs/example_uncalibrated.json:320–325` | 1e-4 m² | 1 cm single-pixel depth sigma |
| `R_rgb` | `configs/example_uncalibrated.json:301–319` | 0.0025 per channel | RGB sigma 0.05 on normalized [0,1] channel |
| `R_model` | `configs/projective_rgbd.json:11–13` | 0 | Model mismatch excluded by default |

At approximately 59 fps (`dt ~ 0.01695 s`), the initial velocity prior alone adds `dt² * 1 = 2.87e-4 m²` to each position variance (1.69 cm standard deviation from this term). A 99% three-dimensional speed-radius of 3.37 m/s implies 5.7 cm movement per frame. This is much larger than a sensible local capture range for many static surfaces.

**Principled calibration:** given an independently justified maximal *plausible* physical speed `v_99` enclosing ~99% of expected motion magnitudes under the model, choose an isotropic starting point `sigma_v = v_99 / sqrt(chi2.ppf(.99,3)) = v_99/3.368`. For example, a **hypothetical** `v_99 = 1.2 m/s` corresponds to sigma ~0.356 m/s and `P_vv ~0.127 (m/s)²`, giving a 99% initial per-frame displacement radius ~2 cm at 59fps. This is an example to illustrate units, **not** a recommendation to hardcode that value across scenes or infer a speed limit from GT. Non-isotropic or learned empirical priors can be more appropriate when externally validated.

Calibrate `q_c` against actual acceleration variability, `R_rgb` and `R_depth` against sensor/renderer uncertainties and view-dependent effects, and include off-diagonal correlations where justified. Keep `P`, `Q`, `R` symmetric PSD/PD with explicit units. The initial posterior `P_xx` is derived via `scene/endpoint.py:48–63` from depth and pixel uncertainty; calibrating sensor noise also changes this prior.

**Crucial:** finite Gaussian covariance expresses a probability distribution, not a hard speed bound. It cannot mathematically prevent arbitrarily large posterior velocities if an incorrect, highly weighted observation remains admitted. A static-point-specific covariance must not be inferred from GT or imposed before motion-coherence estimation. Calibrate common scene/acquisition priors and validate genuine motion retention.

## Safe surgical validation sequence (no implementation changes requested here)

1. **First-bad-update trace**: storage forward point 171031 at frame 1; USB forward point 81029 at frame 2. Use `--debug-point-ids`, `--debug-frames`, factor 1, float64, only free stages. Extract rows from `numeric/trace_frame_XXXX.json`: camera, pixel, source RGB, sampled RGB, depth innovation, `S_zz`, row validity, Jacobian, prior covariance, `delta_x`, `delta_v`, `converged`, and NIS. Find the exact row/state transition producing the first implausible update.
2. **Independent numerical oracle**: replay the same prior and admitted measurements with a dense 6x6 NumPy information-form IEKF; verify sign, gain, covariance and reproducibility. Distinguish algebraic correctness from erroneous observation admission.
3. **Controlled ablations, one variable at a time**: original default versus physically calibrated `P_vv`, `q_c`, `R` under same images, precision, frame cadence, point IDs, all cameras and random seed; separately test careful innovation-consistency / validity policies and nonconvergence acceptance. Do not simultaneously change multiple options.
4. **Regressions**: static raycast scene must not gain false velocity or hallucinated motion; moving blade/stapler/storage/USB trajectories must remain trackable (including actual fast motion). Verify no background or GT enters estimation, no 3DGS, no temporal correspondence, and F1/B1 remain independent.
5. **Statistics to report**: percent accepted points having updates above physically plausible displacement; maximum and quantile `delta_v` at each frame; valid rows before/after each big correction; last observed step; final runaway percent >0.5m, 1m, 3m; static GT error **post hoc**; moving GT error **post hoc**; per-camera prior NIS; acceptance and convergence flags; posterior covariance calibration, not just its PSD.

## Verdict

Confirmed immediate origin: overly large *accepted* projective measurement updates create excessive velocities via `P_vx`, after which invisible points extrapolate without bound. The root enabling weaknesses are insufficient measurement identity/consistency validation, unlimited nonlinear correction acceptance, nonconverged-state acceptance, and a broad illustrative initial velocity covariance. The exact first faulty camera row is not established without per-iteration traces. Changing only `q_c`, censoring nonconverged points, clipping speeds, or attracting all points to static canonical positions would be scientifically unsound and could destroy genuine moving-part recovery.
